# Design — Phase 2 Storage-Aware Shell

## Design goal

The Phase 2 shell must make runtime persistence visible and trustworthy without implying parser, portal, or final-bill capabilities that were not implemented. Operators should be able to see whether Storage is ready, where data is stored, which source bills are persisted, and what audit/failure history exists.

## Navigation sections

The shell keeps the Phase 1 sections:

1. Dashboard
2. Source Bills
3. Enhancement
4. Final Bill
5. Audit / History
6. Settings
7. Diagnostics

Phase 2 adds real data to these views rather than adding decorative screens.

## Dashboard requirements

Dashboard displays:

- Storage root path;
- Storage health status;
- manifest status;
- write/temp probe status;
- active `billSessionId` when present;
- portal status as `NOT VERIFIED` unless later authenticated validation exists.

No fake parser output or portal readiness may be displayed.

## Source Bills view

The Source Bills section shows persisted records from `Storage/Source_Bills`. The table contains imported timestamp, `billSessionId`, original filename, status, and SHA-256 prefix. Missing/corrupt records must be visible as such rather than hidden.

## Audit / History view

The Audit / History section reads persistent audit records from `Storage/Audit`. Reading current state must not itself generate audit records. The view includes safe allowlisted buttons for opening Audit and Failures folders.

## Settings view

Settings displays the actual configured Storage root. It stores only non-secret settings and must not solicit or persist portal passwords, cookies, tokens, or browser session data.

## Diagnostics view

Diagnostics displays the sanitized diagnostic report generated by main process code. It includes:

- storage root;
- health status;
- manifest status;
- read/write/temp probe results;
- recovery summary;
- usage summary;
- source/session/audit/failure record counts.

Diagnostics must not dump arbitrary `process.env`, command lines containing secrets, browser profile contents, cookies, tokens, or auth payloads.

## Visual status language

- `READY` / successful checks use success styling.
- `NOT_INITIALIZED`, `NOT VERIFIED`, `NOT STARTED`, and review states use warning styling.
- `READ_ONLY`, `ACCESS_ERROR`, `CORRUPT`, `ERROR`, and failed states use error styling.

Every status is written as text; color is secondary.

## Interaction boundaries

- All privileged actions go through `window.cghsSuite`.
- `storage.openFolder(folderKey)` accepts only allowlisted Storage folder keys.
- There is no generic command execution, shell execution, Python execution, JavaScript eval, arbitrary file picker outside approved workflows, or unrestricted filesystem browsing.
